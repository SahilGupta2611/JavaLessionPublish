Your destination today

Design request and response DTOs, validate incoming JSON before application behavior, and distinguish input constraints from business rules. Build an account-creation slice with records, Jakarta Validation, explicit mapping, and safe money handling. Allow 3–4 hours including the negative-case lab.

Prerequisites: Day 8 controller/service/repository boundaries, Day 7 RequestBody, and Java records/BigDecimal. Use Java 21 / Boot 3.5 with spring-boot-starter-validation. This remains fictional in-memory practice, without authentication or a durable ledger.

1. Why not expose the domain/entity automatically?

An internal Customer might contain email, phone, identity-document data, passwordHash, riskRating, and internalNotes. Returning it directly can expose fields the client never needed. Accepting it directly can let a caller attempt to set approved, balance, or role.

A DTO, Data Transfer Object, is a deliberately shaped boundary value. A request DTO contains client-writable fields for one operation. A response DTO contains approved output fields. A domain model represents application concepts and rules. A JPA entity later maps persistence state. They may have overlapping fields, but their responsibilities are different.

React form → JSON → CreateAccountRequest (input contract)
    → validation → service → Account (domain) → repository
    → AccountResponse (output contract) → JSON → React

Explicit boundaries let a database column change without necessarily breaking React. They also make accidental exposure visible during review. A DTO is not a complete security system: authorization, deliberate mapping, and allowed-field policies still matter.

2. Java records fit boundary values

public record AccountResponse(
    Long id, String type, String balance, String currency, String status) {}

A record declares its components, canonical constructor, accessors, equals/hashCode, and toString. Accessors are id() rather than getId(). Component references cannot be reassigned; references to mutable lists/objects still require defensive design. Records are not automatically Spring beans and do not need @Component.

Jackson in the course baseline can deserialize records using their constructor and serialize their components. Annotations on components express constraints, but they run only when validation is triggered. Constructing new CreateAccountRequest(...) in arbitrary code does not automatically run Bean Validation.

Records are useful DTOs; they are not an instruction to turn every JPA entity into a record. Persistence libraries have their own entity requirements and lifecycle.

3. Define a narrow CreateAccountRequest

Create domain/AccountType.java:

package com.example.bank.domain;
public enum AccountType { SAVINGS, CURRENT }

Create dto/CreateAccountRequest.java:

package com.example.bank.dto;

import com.example.bank.domain.AccountType;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Positive;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateAccountRequest(
    @NotNull(message = "Customer ID is required")
    @Positive(message = "Customer ID must be positive")
    Long customerId,

    @NotNull(message = "Account type is required")
    AccountType type,

    @NotBlank(message = "Nickname is required")
    @Size(max = 40, message = "Nickname must be at most 40 characters")
    String nickname
) {}

The customer ID is client input in this fixture, not proof of ownership. Later the service verifies authenticated access. The enum restricts account type to known Java constants; it does not check whether a customer is eligible for that type. "UNKNOWN" generally fails JSON-to-enum binding before Bean Validation and produces 400. Null or a missing type is caught by NotNull after binding.

Notice no id, balance, approved, or internal risk fields. The server chooses identity, currency policy, zero opening balance, and status. Accepting those fields from a creation form would blur who controls bank state.

4. Constraint reference with precise null behavior

Annotation Suitable target Meaning Null behavior
@NotNull Any reference Must be present/non-null Rejects null
@NotBlank String Contains a non-whitespace character Rejects null
@Positive Numeric value Strictly greater than zero Null valid; pair with NotNull
@PositiveOrZero Numeric value Zero or positive Null valid; pair with NotNull
@Size String/collection/map/array Bounds length/size Null valid
@Email String Email syntax constraint Null valid; pair with NotBlank if required
@Valid Nested value / bound input Cascade/trigger validation Does not itself require non-null

@Size(min=2,max=80) bounds a name's length; it does not prove it is a real legal name. @Email checks syntax according to the provider, not mailbox ownership or deliverability. @Positive works on BigDecimal but does not check currency precision. @PositiveOrZero is appropriate for a server-side balance invariant, not permission for clients to set balances.

public record CreateCustomerRequest(
    @jakarta.validation.constraints.NotBlank
    @jakarta.validation.constraints.Size(min = 2, max = 80)
    String name,
    @jakarta.validation.constraints.NotBlank
    @jakarta.validation.constraints.Email
    String email) {}

This focused snippet demonstrates constraints; the complete lab uses CreateAccountRequest. Friendly custom messages help clients explain corrections. Do not leak sensitive internal state in validation messages. Messages alone do not define an HTTP error format.

5. @Valid at the controller boundary

@PostMapping
public ResponseEntity<AccountResponse> create(
    @Valid @RequestBody CreateAccountRequest request) {
    Account account = service.create(request);
    return ResponseEntity.created(URI.create("/api/accounts/" + account.id()))
        .body(AccountResponse.from(account));
}

This is a focused method excerpt; the complete controller below supplies imports and fields. @RequestBody selects body binding. @Valid requests Bean Validation of the bound DTO. If component constraints fail, Spring rejects the request before invoking this method. A missing body, malformed JSON, wrong enum string, and valid JSON with invalid fields fail at different stages, even though they commonly result in 400.

For ordinary DTO argument validation, Spring raises MethodArgumentNotValidException. Framework versions with built-in method validation can raise HandlerMethodValidationException for other signatures. Do not assume every 400 has the same exception class. Day 10 will centralize safe formatting for these failure categories.

6. What happens on invalid input?

POST /api/accounts HTTP/1.1
Content-Type: application/json

{"customerId":-7,"type":null,"nickname":"   "}

Deserialization can create the record because these values have the right basic JSON types. Bean Validation then reports a nonpositive customer ID, missing type, and blank nickname. The controller body and service creation are not invoked. No ID should be allocated and no account inserted.

HTTP/1.1 400 Bad Request

The baseline framework returns an error response, but its exact body depends on Boot configuration, exception handling, and content negotiation. Do not promise a field-errors array without implementing it. A future standardized contract could look like:

{
  "code": "VALIDATION_FAILED",
  "errors": [
    {"field":"customerId","message":"Customer ID must be positive"},
    {"field":"nickname","message":"Nickname is required"}
  ]
}

This JSON is a target contract for Day 10, not the current mini app's guaranteed response. React can initially show a generic invalid-input message based on 400, then map structured field errors after the server actually implements that contract. Malformed JSON cannot always be mapped to a DTO field neatly.

7. Complete account-creation mini app

These files form a complete replacement account slice. Keep BankingApplication and unrelated routes. Replace Day 8 Account.java, AccountRepository, InMemoryAccountRepository, AccountService, AccountResponse, and AccountController with these versions. Keep AccountNotFoundException from Day 8 and add the enum/request above. The expanded Account record means Day 8 transfer-preview code must be adapted if you retain it; this slice focuses only on account creation/read.

Create domain/Account.java:

package com.example.bank.domain;
import java.math.BigDecimal;

public record Account(
    Long id, Long customerId, AccountType type, String nickname,
    BigDecimal balance, String currency, String status) {}

Create dto/AccountResponse.java:

package com.example.bank.dto;
import com.example.bank.domain.Account;

public record AccountResponse(
    Long id, String type, String nickname,
    String balance, String currency, String status) {
    public static AccountResponse from(Account account) {
        return new AccountResponse(account.id(), account.type().name(),
            account.nickname(), account.balance().toPlainString(),
            account.currency(), account.status());
    }
}

This mapper is explicit: internal customer linkage is omitted, type becomes a documented string, and balance becomes a decimal string. No mapping framework is required for six fields. A separate mapper class may become useful as mappings grow.

Create repository/AccountRepository.java:

package com.example.bank.repository;
import com.example.bank.domain.Account;
import java.util.Optional;

public interface AccountRepository {
    long nextId();
    Account save(Account account);
    Optional<Account> findById(Long id);
}

Create repository/InMemoryAccountRepository.java:

package com.example.bank.repository;

import com.example.bank.domain.Account;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.stereotype.Repository;

@Repository
public class InMemoryAccountRepository implements AccountRepository {
    private final AtomicLong sequence = new AtomicLong(100);
    private final ConcurrentHashMap<Long, Account> data = new ConcurrentHashMap<>();

    @Override
    public long nextId() { return sequence.incrementAndGet(); }

    @Override
    public Account save(Account account) {
        data.put(account.id(), account);
        return account;
    }

    @Override
    public Optional<Account> findById(Long id) {
        return Optional.ofNullable(data.get(id));
    }
}

AtomicLong allocates distinct IDs within this one process. ConcurrentHashMap supports concurrent map operations. Neither supplies a durable transaction, cross-instance uniqueness, or crash recovery. A database eventually owns durable identity/constraints. Gaps in an ID sequence are normal and are not evidence of missing money.

Create service/AccountService.java:

package com.example.bank.service;

import com.example.bank.domain.Account;
import com.example.bank.dto.CreateAccountRequest;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.repository.AccountRepository;
import java.math.BigDecimal;
import org.springframework.stereotype.Service;

@Service
public class AccountService {
    private final AccountRepository repository;
    public AccountService(AccountRepository repository) {
        this.repository = repository;
    }

    public Account create(CreateAccountRequest request) {
        // Fictional customer registry: only customer 7 exists in this exercise.
        if (!Long.valueOf(7).equals(request.customerId())) {
            throw new IllegalArgumentException("Customer is not eligible for this demo");
        }
        Account account = new Account(repository.nextId(), request.customerId(),
            request.type(), request.nickname().trim(),
            new BigDecimal("0.00"), "INR", "ACTIVE");
        return repository.save(account);
    }

    public Account get(Long id) {
        return repository.findById(id)
            .orElseThrow(() -> new AccountNotFoundException(id));
    }
}

The service accepts a request DTO as a pragmatic small-app choice. A more independent application boundary can map into CreateAccountCommand first. The service owns opening balance/currency/status, while validation annotations guard the HTTP input shape. Direct callers still need a valid command; annotations don't run automatically on arbitrary method calls.

Create controller/AccountController.java:

package com.example.bank.controller;

import com.example.bank.dto.AccountResponse;
import com.example.bank.dto.CreateAccountRequest;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.service.AccountService;
import jakarta.validation.Valid;
import java.net.URI;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/accounts")
public class AccountController {
    private final AccountService service;
    public AccountController(AccountService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<AccountResponse> create(
        @Valid @RequestBody CreateAccountRequest request) {
        try {
            var account = service.create(request);
            return ResponseEntity.created(URI.create("/api/accounts/" + account.id()))
                .body(AccountResponse.from(account));
        } catch (IllegalArgumentException ex) {
            // Demo eligibility failure; Day 10 adds specific exceptions/formatting.
            return ResponseEntity.badRequest().build();
        }
    }

    @GetMapping("/{id}")
    public ResponseEntity<AccountResponse> get(@PathVariable("id") Long id) {
        try {
            return ResponseEntity.ok(AccountResponse.from(service.get(id)));
        } catch (AccountNotFoundException ex) {
            return ResponseEntity.notFound().build();
        }
    }
}

This local catch handles one known demonstration business failure. Do not generalize it into catch-all validation handling. Input constraint failures occur before this method body. A production API would define a specific eligibility exception and suitable documented status, and centralize translation on Day 10.

POST /api/accounts HTTP/1.1
Content-Type: application/json

{"customerId":7,"type":"SAVINGS","nickname":"Travel fund"}

HTTP/1.1 201 Created
Location: /api/accounts/101
Content-Type: application/json

{"id":101,"type":"SAVINGS","nickname":"Travel fund","balance":"0.00","currency":"INR","status":"ACTIVE"}

Your exact ID depends on previous successful creations in the process. Use the returned Location/ID rather than assuming 101.

8. TransferRequest: structural versus business validation

Create this DTO as a next-step contract; it is not a promise that a transfer execution endpoint exists in this mini app.

package com.example.bank.dto;

import jakarta.validation.constraints.*;
import java.math.BigDecimal;

public record TransferRequest(
    @NotNull @Positive Long fromAccountId,
    @NotNull @Positive Long toAccountId,
    @NotNull @Positive
    @Digits(integer = 12, fraction = 2)
    BigDecimal amount,
    @NotBlank @Pattern(regexp = "INR") String currency,
    @Size(max = 140) String reference
) {}

NotNull + Positive rejects missing, zero, and negative values. Digits bounds decimal precision for this INR-only example. Pattern restricts currency rather than accepting every three-letter string. A multi-currency service must define supported codes and each currency's precision; two fraction digits is not universal. Optional reference can be null; Size only bounds it when present.

Input validation: IDs supplied and positive, amount positive, precision supported, strings within bounds. Business validation: accounts exist and are active, caller owns source, currencies match, sufficient available funds, daily limit remaining, account IDs differ. Cross-field “from differs from to” can be a custom class-level constraint, but still does not replace stateful service checks.

A positive amount of 5000 passes input validation even if balance is 3000. Only a service with access to authoritative state can reject insufficient funds. Recheck at execution under concurrency/transaction protection; a prior preview is not a reservation.

9. BigDecimal for money

BigDecimal amount = new BigDecimal("5000.00");
BigDecimal balance = new BigDecimal("50000.00");

if (balance.compareTo(amount) >= 0) {
    BigDecimal remaining = balance.subtract(amount);
}

Import java.math.BigDecimal in the file using this fragment. BigDecimal methods return new values; balance.subtract(amount) does not mutate balance. compareTo compares numeric value. equals also compares scale: new BigDecimal("10.0") is not equals to new BigDecimal("10.00"), though compareTo returns zero.

BigDecimal normalized = amount.setScale(2, java.math.RoundingMode.UNNECESSARY);

UNNECESSARY rejects values that would require rounding. Where rounding is legitimate, specify the bank's policy explicitly instead of choosing a random mode. Currency conversion/fees also need clear rounding points. Frontend number arithmetic uses binary floating point; preserve decimal strings in form state/payload when practical and use a documented exact-decimal server contract. Jackson in this baseline can bind decimal strings into BigDecimal; stricter coercion settings can change that behavior, so the API and tests must agree.

10. Nested validation and enum concepts

public record AddressRequest(
    @jakarta.validation.constraints.NotBlank String line1,
    @jakarta.validation.constraints.NotBlank String city,
    @jakarta.validation.constraints.Pattern(regexp = "[0-9]{6}") String postalCode) {}

public record CustomerWithAddressRequest(
    @jakarta.validation.constraints.NotBlank String name,
    @jakarta.validation.constraints.NotNull
    @jakarta.validation.Valid AddressRequest address) {}

These types go in separate files if public. Valid cascades into AddressRequest; NotNull requires the nested object. Pattern permits null, so add NotBlank if postalCode must be present. The six-digit pattern is a local teaching contract, not a worldwide address policy.

Enums constrain known values but need eligibility rules separately. NotBlank is unsuitable for an enum object; use NotNull. A String field may use Pattern or a custom constraint, while a typed enum catches unrecognized names during deserialization. Neither tells you whether that account type is allowed for this customer today.

11. Sensitive fields and over-posting

{
  "customerId":7,
  "type":"SAVINGS",
  "nickname":"Travel fund",
  "balance":"999999.00",
  "approved":true
}

A naive domain-binding controller could accept dangerous fields if they exist on its input model. Our request DTO has no balance/approved fields and mapping explicitly constructs zero balance. Unknown JSON property handling depends on configuration; Boot may ignore unknown properties unless strict failure is enabled. Either way, the DTO cannot grant these omitted capabilities. Decide whether to reject unknown fields for your contract and test it.

Returning a broad entity and relying on the frontend to hide fields is unsafe: anyone can inspect the network response. DTOs should omit password hashes, secret tokens, full identity documents, and internal risk notes. Masking a value is an explicit output decision; do not invent fake security by renaming a property.

12. React form to validated DTO

async function createAccount(form) {
  const response = await fetch("/api/accounts", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({
      customerId: 7,
      type: form.type,
      nickname: form.nickname
    })
  });
  if (response.status === 400) {
    throw new Error("Check the account fields and customer eligibility");
  }
  if (!response.ok) throw new Error(`Create failed: ${response.status}`);
  return response.json();
}

The form should also validate for fast feedback, but the server repeats checks because clients are untrusted. Don't send every component state field with JSON.stringify(form) unless every field is intentionally part of the request contract. Server validation messages will become field-specific after Day 10's response formatting; this example avoids assuming that format already exists.

For a transfer form, keep amount as text such as "5000.00" until validation/serialization. Do not turn it into a floating-point number, subtract locally, and claim a settled balance. The response from the bank is authoritative.

13. Common mistakes clinic

  • Annotations without Valid: constraints may never run at the HTTP boundary.
  • Valid without a validation provider/starter: add the compatible validation dependency.
  • javax.validation mixed with jakarta.validation: Boot 3 uses Jakarta imports; use one coherent baseline.
  • Positive alone on a nullable amount: null passes; pair with NotNull.
  • NotBlank on enum/number: use an annotation suitable for the type.
  • Email proves ownership: syntax validation does not verify mailbox control.
  • DTO treated as authorization: allowed shape does not grant access.
  • Returning entities blindly: internal fields/relationships can escape.
  • Money stored as double: choose BigDecimal and clear precision/rounding policy.
  • Assuming default field-error JSON: implement and test the format first.
  • Nested object lacks Valid: its component constraints may not cascade.

14. Why this matters in real work

DTOs make contracts reviewable and limit accidental coupling/exposure. Validation rejects bad input early and consistently, while services protect state-dependent invariants. Exact money representation prevents rounding surprises. This separation helps React forms explain errors without giving frontend code authority over bank rules.

15. Hands-on lab: positive and negative cases

  1. Build the complete replacement account slice with the validation starter.
  2. Create a valid account, GET the returned Location, and verify opening balance is 0.00.
  3. Send missing customerId, negative customerId, null type, unknown enum, blank nickname, and 41-character nickname; expect 400.
  4. Send malformed JSON; identify why it fails before DTO validation.
  5. Send customerId 8 with otherwise valid fields; explain the difference between valid input and failed demo eligibility.
  6. Attempt over-posting balance/approved fields. Verify the returned/stored account still has the server-selected balance/status.
  7. Add a required nested address to a customer request and prove both missing address and blank city are rejected.
  8. Record whether your default errors include field details; do not alter React to expect details you did not observe.

Acceptance criteria: invalid requests create no accounts, response fields are explicit, server-owned balance cannot be set by input, enum/type mismatches are handled, and validation versus business rules can be explained separately. Do not log complete request bodies containing personal/financial data while debugging.

Challenge: define a multi-currency TransferRequest and a service policy that validates supported currency/decimal places. Test 0, negative, null, 12.345 INR, same account IDs, inactive account, and insufficient funds. Explain which cases can be rejected without a database lookup and which require authoritative account state. Do not execute actual transfers in this lab.

16. Knowledge check

1. Does Positive reject null?

No. Combine it with NotNull for a required numeric field.

2. Does an annotation run when you call new on a DTO?

Not by itself. A validation entry point, such as Valid on a bound controller argument or an explicit Validator, must trigger it.

3. Why separate request and response DTOs?

Clients can write only permitted input fields, while output exposes only deliberate safe fields. Their shapes can differ.

4. Is sufficient balance a Bean Validation field constraint?

It requires current account state and belongs in business behavior, rechecked safely at execution.

5. Why use compareTo for BigDecimal comparisons?

It compares numerical value independently of scale; equals also checks scale.

6. Does Valid make a nested address required?

No. It cascades validation when an object is present. Add NotNull to require the object.

7. What happens when the enum JSON is UNKNOWN?

Binding normally fails before ordinary field validation, yielding a request error. Exact formatting is a separate exception-handling concern.

17. Cheat sheet

Request DTO = permitted input. Response DTO = approved output. Domain/entity = internal application/persistence concepts. Records are concise boundary values. Jakarta constraints + Valid + provider trigger input checks. NotNull pairs with nullable numeric constraints. Business rules require service/state. BigDecimal handles decimals; choose rounding and wire format deliberately. Next: Day 10 will give validation and business failures a consistent, safe API error format.
