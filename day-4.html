Your destination today

By the end, you should be able to design a banking endpoint, explain every part of its HTTP exchange, choose a method and status code, and call it from React. You will write an API contract before writing a Spring controller. Allow 2–3 hours including the lab; revisit the examples until you can predict the response without looking.

Prerequisites: Java objects, interfaces, collections, and basic JavaScript fetch. No Spring installation is required today. Recap: a Java object exists inside a running process. An HTTP response moves a representation of that object across a network. Your React app cannot directly invoke a Java method in another process.

1. Two programs, one conversation

Imagine React shows a customer's account balance. The browser knows how to display data; the bank's server knows which account belongs to that customer and stores the authoritative balance. HTTP, Hypertext Transfer Protocol, gives both programs a shared request/response format.

React component → fetch → HTTP request → server route
                                              ↓
                                    application rules + data
                                              ↓
React state ← parsed JSON ← HTTP response ← result

A request is an instruction or question. A response reports the result. The server can reject a request even if the UI button was enabled. Frontend validation improves usability; backend validation protects the data. Reloading React does not reset a server database. Restarting our later in-memory practice backend does reset its data.

Banking mental model: the browser is a customer at a service desk, the URL identifies the desk/resource, the method describes the requested operation, headers are context, and the body is the filled form. The response has an outcome code and, sometimes, a receipt. This analogy explains structure, not authentication: real ownership checks must be implemented on the server.

HTTP is stateless at the protocol level: each request must carry enough context for the server to understand it. Applications can still keep data, sessions, and balances. Stateless does not mean “the bank forgets your account.” Use HTTPS for banking communications: it protects transport; it does not replace permissions checks.

2. Read a complete exchange

GET /api/accounts/101?includeRecentTransactions=true HTTP/1.1
Host: localhost:8080
Accept: application/json
Authorization: Bearer example-token

Line 1 contains the method, request target, and protocol version. /api/accounts/101 identifies one account. The part after ? is a query string. Host identifies the server. Accept says what response formats the client can understand. Authorization carries credentials; the example token is a placeholder, not a working login. A GET normally has no body. HTTP/2 and HTTP/3 encode messages differently, but these conceptual pieces remain.

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-store

{
  "id": 101,
  "customerId": 7,
  "type": "SAVINGS",
  "balance": "50000.00",
  "currency": "INR"
}

200 communicates success. Content-Type describes the response body. The blank line separates headers from the body in this readable HTTP/1.1 notation. Cache-Control: no-store asks caches not to store the response; sensitive responses need a deliberate cache policy. The balance is a JSON string here to retain an exact decimal representation at the JavaScript boundary. Your API must document whether money is a decimal string or number, and use the choice consistently.

Request anatomy: method + URL + headers + optional body. Response anatomy: status + headers + optional body. A 204 response has no body; do not call response.json() on it.

3. REST starts with resources

REST is an architectural style, not a Java library. In a resource-oriented API, account, customer, beneficiary, transfer, and transaction are resources with stable addresses. A representation describes the resource, commonly using JSON. The method conveys the operation, so URLs usually do not need verbs.

Resource Collection URL Individual URL Meaning
Customer /api/customers /api/customers/7 Person/profile
Account /api/accounts /api/accounts/101 Account summary
Beneficiary /api/customers/7/beneficiaries /api/customers/7/beneficiaries/12 Approved payee
Transfer /api/transfers /api/transfers/9001 Transfer instruction/result
Transaction /api/accounts/101/transactions /api/transactions/3001 Recorded ledger entry

Prefer /api/accounts/101 over /getAccount?id=101, and /api/transfers over /doTransferNow. Plural nouns make collections predictable. Nested URLs express relationships; a server must still check that beneficiary 12 belongs to customer 7. Avoid deeply nesting everything: a transaction can have its own canonical URL.

A transfer and a transaction are related but not necessarily the same thing. One transfer may produce a debit entry and a credit entry. Later you may model pending, failed, or reversed transfers. Naming the resources clearly keeps frontend assumptions honest.

4. Methods and CRUD

CRUD means Create, Read, Update, Delete. HTTP methods express related intentions, but business operations are richer than four database actions.

Method Typical URL CRUD intention Body Typical success
GET /api/accounts/101 Read None 200 + representation
POST /api/accounts Create Creation fields 201 + created resource
PUT /api/customers/7 Replace writable representation All writable fields 200 or 204
PATCH /api/customers/7 Apply partial change Defined patch format 200 or 204
DELETE /api/customers/7/beneficiaries/12 Remove resource Usually none 204

GET must not transfer money or alter a balance. A browser, cache, or monitoring system can repeat GET automatically. POST /api/transfers creates a transfer instruction. It must not mean “blindly set both balances.” Account closure is usually a business workflow with balance, compliance, and retention checks, rather than deleting a historical account row.

PUT says “make the writable representation look like this.” A missing writable field is not automatically “keep the old value.” PATCH says “apply this specified change.” PATCH is not just an incomplete PUT: document missing fields, explicit null, and patch media type. Day 7 implements one small patch contract.

5. Idempotency and retries

An operation is idempotent when repeating the same request has the same intended server effect as doing it once. It does not mean every response is identical.

GET is safe and idempotent. PUT and DELETE are idempotent by their semantics. Deleting a beneficiary twice may return 204 first and 404 second, while the final state remains “beneficiary absent.” POST is not generally idempotent: sending the same transfer twice may debit twice. PATCH can be idempotent when setting nickname to a value; a patch that increments a counter is not.

POST /api/transfers HTTP/1.1
Content-Type: application/json
Idempotency-Key: transfer-client-generated-uuid

{"fromAccountId":101,"toAccountId":102,"amount":"5000.00","currency":"INR"}

If the network times out, the server may already have processed the transfer. A real idempotency-key implementation stores the key, request identity, and result durably and atomically, and rejects reuse with a different payload. Adding a header alone does nothing. Our early lessons do not implement this guarantee. Disable-double-click is helpful UX but cannot prevent all duplicate requests.

6. JSON is text, not a shared object

JSON supports objects, arrays, strings, numbers, booleans, and null. Property names and strings use double quotes. Comments, trailing commas, undefined, and functions are not JSON.

const draft = { customerId: 7, type: "SAVINGS" };
const body = JSON.stringify(draft); // JavaScript object → JSON text
const result = JSON.parse('{"id":101}'); // JSON text → JS object

Serialization turns an in-process object into a transferable representation. Deserialization does the reverse. Spring typically uses Jackson to convert Java objects and JSON. A Java Long or BigDecimal is not literally sent as a Java object. Date/time, enum, and money formats are part of the API contract. JavaScript integers beyond its safe integer range also need a documented string representation.

// Conceptual response model; Spring serialization comes in Day 6.
public record AccountView(
    Long id, String type, String balance, String currency) {}

The record defines named components. A record is immutable in the sense that its component references cannot be reassigned; mutable referenced objects still need care. An instance might become {"id":101,"type":"SAVINGS","balance":"50000.00","currency":"INR"} on the wire.

7. Path, query, or body?

Use a path variable to identify a resource: 101 in /api/accounts/101. Use query parameters to shape a retrieval: /api/transactions?accountId=101&type=DEBIT&page=0&size=20. Use a request body for a structured creation or change.

POST /api/customers HTTP/1.1
Content-Type: application/json
Accept: application/json

{"name":"Asha Rao","email":"asha@example.com"}

Do not put account passwords or transfer payloads in query strings: URLs are often recorded in logs and browser history. Do not use a GET body to implement filtering; interoperability is poor. Encode query values instead of concatenating arbitrary user text. In JavaScript, URLSearchParams handles encoding.

const query = new URLSearchParams({ type: "DEBIT", page: "0" });
const response = await fetch(`/api/accounts/101/transactions?${query}`);

8. Headers you will actually use

Content-Type: application/json means “the body I am sending is JSON.” It is distinct from Accept: application/json, which requests a JSON response. A missing or incompatible request Content-Type may produce 415 Unsupported Media Type, rather than a validation error.

Authorization: Bearer ... commonly carries an access token. It should be read from an established authentication flow, not hardcoded in a component. The backend validates it and checks permissions. Location in a 201 response identifies the newly created resource. Headers are metadata; do not encode business fields in custom headers merely because you can.

React on port 5173 and Spring on 8080 are different origins. Relative /api/... calls need a development proxy or a same-origin deployment. If you call http://localhost:8080 directly, configure a restricted development CORS policy. CORS is browser access control, not authentication. A JSON cross-origin POST can trigger a preflight OPTIONS request before your POST.

9. Status codes tell the client what happened

Status Meaning Banking example UI response
200 OK Successful response with data Account found Render balance
201 Created New resource created Transfer instruction stored Show receipt
204 No Content Success without body Beneficiary removed Remove row
400 Bad Request Invalid input/request Negative transfer amount Show form errors
401 Unauthorized Missing/invalid authentication Expired token Start login flow
403 Forbidden Authenticated but not permitted Other customer's account Show access denial
404 Not Found Resource absent/not exposed Unknown account Show not found
409 Conflict Request conflicts with current state Duplicate beneficiary Explain conflict
500 Internal Server Error Unexpected server failure Unhandled defect Show retry/support message

401 is about authentication; 403 is about permission. Some systems deliberately return 404 for resources the user must not discover. Insufficient funds is a business rejection; 409 is one reasonable documented choice, not a universal mandated status. A server bug is not a client's 400. Do not return 200 with {"success":false} for every failure: clients, monitoring, and proxies use status codes.

10. Successful and rejected transfers

HTTP/1.1 201 Created
Location: /api/transfers/9001
Content-Type: application/json

{"id":9001,"status":"PENDING","amount":"5000.00","currency":"INR"}

201 means the transfer resource was created, not necessarily that settlement finished. Choose PENDING or SUCCESS according to actual behavior. For asynchronously accepted work, 202 Accepted is another useful contract; do not label unfinished work as successful settlement.

HTTP/1.1 400 Bad Request
Content-Type: application/json

{"code":"INVALID_AMOUNT","message":"Amount must be greater than zero"}

HTTP/1.1 409 Conflict
Content-Type: application/json

{"code":"INSUFFICIENT_FUNDS","message":"Available balance is too low"}

These error bodies are proposed contracts, not Spring's guaranteed default output. Day 10 will standardize formatting. Never include stack traces, credentials, or full account numbers in a client error.

11. React consumes the contract

async function initiateTransfer(draft) {
  const response = await fetch("/api/transfers", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json"
    },
    body: JSON.stringify(draft)
  });
  const payload = await response.json();
  if (!response.ok) {
    throw new Error(payload.message ?? `Request failed: ${response.status}`);
  }
  return payload;
}

fetch resolves even for HTTP 400/500, so check ok. It rejects for network failures. JSON.stringify is necessary because the request body is text. response.json() asynchronously parses the response. This example assumes the documented JSON contract; a production client also handles empty/non-JSON responses. Display amounts using decimal-aware formatting and do not use floating-point arithmetic to make financial decisions in the UI.

12. Why this matters in backend work

An API contract is a collaboration agreement. A frontend can implement loading states, forms, and errors before database code exists. A backend can evolve internal storage without changing the contract. Clear resource names and status codes make integration tests, support tools, and incident diagnosis easier. For banking, duplicate processing, ownership, and money representation are design concerns from the first endpoint, not finishing touches.

13. Common mistakes clinic

  • GET /transfer?amount=5000: GET is safe; create a transfer using POST.
  • Putting every field in the URL: identifiers and filters belong there, structured change data belongs in a body.
  • Confusing Content-Type and Accept: one describes the sent body; the other requests a response format.
  • Treating 201 as settled money: creation and settlement are different outcomes.
  • Retrying an uncertain transfer blindly: use a durable idempotency design or reconcile its status.
  • Calling JSON parsing after 204: there is nothing to parse.
  • Trusting hidden React controls for security: permissions must be enforced server-side.

14. Hands-on lab: design the bank's API

Work in a document or API client; no running server is required. Create contracts for account lookup, customer creation, beneficiary removal, transaction filtering, and transfer initiation.

  1. For each operation, write method, URL, path/query/body fields, request headers, success status, and example JSON.
  2. Add a 404 account lookup, a 400 invalid customer email, and a 409 duplicate beneficiary. Write how React should react to each.
  3. Decide whether transfer creation means pending or settled. Add a status lookup endpoint so an uncertain client can reconcile.
  4. Write a fetch function for account lookup that checks response.ok, and one for deletion that does not parse a 204 body.
  5. Review the URLs: remove verbs where a resource and method express the operation.

Acceptance criteria: five clear contracts, no modifying GET, no secret URL parameters, 201 with Location for creation, no body on 204, and a documented money representation. Explain why repeating a transfer POST is riskier than repeating an account GET.

Challenge: draw a timeout timeline where the server creates a transfer but React never sees the receipt. Specify what an idempotency key must store and how a reused key with a different amount should be rejected. Do not claim you have implemented this simply by sending the header.

15. Knowledge check — predict before opening

1. Is a repeated DELETE allowed to return a different status and still be idempotent?

Yes. Idempotency describes intended state/effect. The resource can remain absent after both calls even if the second returns 404.

2. Where does a transaction date-range filter belong?

In query parameters, such as ?from=2026-10-01&to=2026-10-05. Document inclusive/exclusive boundaries and timezone.

3. Why does fetch not enter catch for every 400?

HTTP errors still produce responses. Check response.ok and throw or branch explicitly; network failures reject the promise.

4. Does JSON contain Java class instances?

No. It is a transferable data representation. Jackson reconstructs a Java value using the target type and configuration.

5. Is Authorization enough to access any account ID?

No. Authentication identifies the caller; authorization checks their permission for that specific account.

6. What should a client do after 204?

Treat the action as successful without trying to parse a response body.

16. Cheat sheet

Path = identity. Query = retrieval options. Body = structured input. GET reads, POST creates/initiates, PUT replaces, PATCH changes selected fields, DELETE removes. Content-Type describes the body; Accept requests a representation. Check HTTP status before assuming success. Use decimal money contracts. A retry can be a new financial action unless the server implements idempotency. Next: turn these contracts into a running Spring Boot application.
