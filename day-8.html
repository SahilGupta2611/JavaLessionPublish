Your destination today

Understand and build Controller → Service → Repository with constructor injection. Follow an account request end to end, replace a repository without changing its caller, and coordinate transfer rules through interfaces. This is the bridge from Day 2's OOP to everyday Spring development. Allow 3–4 hours; the request-tracing exercises are as important as the code.

Prerequisites: Java interfaces/implements/final from Day 2, collections and Optional from Day 3, and Spring controllers/CRUD from Days 5–7. Examples target Java 21 / Boot 3.5. This page provides a complete account-read slice and a transfer-eligibility preview, not an actual money-transfer implementation.

1. Why one controller eventually becomes a problem

Imagine the transfer controller parses JSON, validates accounts, checks funds, calculates a fee, changes a map, writes a transaction, formats JSON, and sends notifications. Now a scheduled job also needs to initiate transfers. It cannot reuse those rules without pretending to be an HTTP request. Unit tests need HTTP plumbing just to check a balance rule. Replacing the map with PostgreSQL touches the controller everywhere.

Separation of concerns gives each collaborator one primary reason to change:

Layer Question it answers Banking responsibility Typical reason to change
Controller How does HTTP enter/leave? URLs, binding, status, DTOs API contract changes
Service What should the application do? Account eligibility, transfer rules Business policy changes
Repository How is data retrieved/stored? Find/save accounts Storage implementation changes
Domain What are the core values/concepts? Account, Money, Transfer Domain model changes

A service is not just “the file between two other files.” If it coordinates nothing yet, it can still provide a stable application boundary, but do not invent dozens of layers without a purpose. The goal is readable ownership of rules, not ceremonial forwarding methods.

2. Dependency direction and request direction

React → HTTP → AccountController → AccountService → AccountRepository
                                         ↓                 ↑
                                     domain values    InMemoryAccountRepository

Response travels back: domain → response DTO → JSON → React

The controller depends on application behavior. The service depends on a repository abstraction, not on HashMap details or SQL. The repository implementation supplies the storage mechanism. The service does not call back into the controller. React does not know which repository implementation is in use.

Dependency direction is a design relationship. Request flow is the runtime sequence of calls. An interface can be defined near the application layer while implemented by storage code, letting the application depend on a contract rather than storage technology. That is the dependency inversion link to Day 2.

4. Domain model: money stays decimal

Create domain/Account.java:

package com.example.bank.domain;

import java.math.BigDecimal;

public record Account(
    Long id, Long customerId, String type,
    BigDecimal balance, String currency, boolean active) {}

This record represents an application value, not an HTTP contract and not a JPA entity. A JPA entity later has persistence identity/mapping behavior; do not treat all three terms as interchangeable. We use BigDecimal for exact decimal arithmetic. Construct decimal values from strings, because new BigDecimal(0.1) imports a binary floating-point approximation.

active matters to transfer rules but may not belong in every API response. A domain type can contain data that the public contract should omit. This distinction becomes central on Day 9.

5. Repository contract first

Create repository/AccountRepository.java:

package com.example.bank.repository;

import com.example.bank.domain.Account;
import java.util.List;
import java.util.Optional;

public interface AccountRepository {
    Optional<Account> findById(Long id);
    List<Account> findByCustomerId(Long customerId);
}

interface describes available behavior. Optional<Account> says lookup can be absent. List<Account> says a customer can have zero or many accounts. The contract does not expose HashMap, SQL rows, HTTP statuses, or JSON. It has no annotation because Spring needs a concrete implementation to instantiate.

This is a read-only contract today. Add writes when a service actually needs them. Smaller contracts reduce the operations a caller can accidentally misuse. A repository should not decide whether to return 404; that is an HTTP concern above it.

6. In-memory implementation

Create repository/InMemoryAccountRepository.java:

package com.example.bank.repository;

import com.example.bank.domain.Account;
import java.math.BigDecimal;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Repository;

@Repository
public class InMemoryAccountRepository implements AccountRepository {
    private final Map<Long, Account> data = Map.of(
        101L, new Account(101L, 7L, "SAVINGS",
            new BigDecimal("50000.00"), "INR", true),
        102L, new Account(102L, 7L, "CURRENT",
            new BigDecimal("20000.00"), "INR", true),
        103L, new Account(103L, 8L, "SAVINGS",
            new BigDecimal("100.00"), "INR", false)
    );

    @Override
    public Optional<Account> findById(Long id) {
        return Optional.ofNullable(data.get(id));
    }

    @Override
    public List<Account> findByCustomerId(Long customerId) {
        return data.values().stream()
            .filter(a -> a.customerId().equals(customerId))
            .sorted(java.util.Comparator.comparing(Account::id))
            .toList();
    }
}

implements promises this class provides the interface methods. @Override lets the compiler check signatures. @Repository makes it a data-access bean discovered by Spring. The fixed map is safe for concurrent reads and convenient for a reproducible exercise. It is not persistent storage. Spring does not secretly connect this class to a database merely because the annotation says Repository.

Later a JDBC/JPA adapter could implement the same contract. AccountService would still call findById; the implementation would translate database results into the domain representation. A durable database can add constraints, locking, and transactions that this fixture lacks.

7. Application service and missing-resource exception

Create exception/AccountNotFoundException.java:

package com.example.bank.exception;

public class AccountNotFoundException extends RuntimeException {
    public AccountNotFoundException(Long id) {
        super("Account not found: " + id);
    }
}

Create service/AccountService.java:

package com.example.bank.service;

import com.example.bank.domain.Account;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.repository.AccountRepository;
import java.util.List;
import org.springframework.stereotype.Service;

@Service
public class AccountService {
    private final AccountRepository repository;

    public AccountService(AccountRepository repository) {
        this.repository = repository;
    }

    public Account get(Long id) {
        return repository.findById(id)
            .orElseThrow(() -> new AccountNotFoundException(id));
    }

    public List<Account> forCustomer(Long customerId) {
        return repository.findByCustomerId(customerId);
    }
}

@Service communicates application/business responsibility and registers a bean. The final field holds the dependency reference. final prevents reassignment; it does not make the repository's contents immutable. The constructor requires a fully supplied repository. orElseThrow turns absence into an application failure; it does not know HTTP 404.

The service is directly constructible in plain Java tests. It has no dependency on servlet requests or ResponseEntity. It is a simple boundary today; business rules can grow here without moving them into the controller or repository.

8. DTO mapping at the HTTP boundary

Create dto/AccountResponse.java:

package com.example.bank.dto;

import com.example.bank.domain.Account;

public record AccountResponse(
    Long id, String type, String balance, String currency) {
    public static AccountResponse from(Account account) {
        return new AccountResponse(account.id(), account.type(),
            account.balance().toPlainString(), account.currency());
    }
}

The mapper deliberately exposes only fields required by the client. toPlainString produces decimal text without scientific notation. We do not expose internal customerId or active in this particular response. Another authorized customer dashboard contract may intentionally include them. Explicit choice is the point.

Create the replacement controller/AccountController.java:

package com.example.bank.controller;

import com.example.bank.dto.AccountResponse;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.service.AccountService;
import java.util.List;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/accounts")
public class AccountController {
    private final AccountService service;

    public AccountController(AccountService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public ResponseEntity<AccountResponse> get(@PathVariable("id") Long id) {
        try {
            return ResponseEntity.ok(AccountResponse.from(service.get(id)));
        } catch (AccountNotFoundException ex) {
            return ResponseEntity.notFound().build();
        }
    }

    @GetMapping
    public List<AccountResponse> list(
        @RequestParam("customerId") Long customerId) {
        return service.forCustomer(customerId).stream()
            .map(AccountResponse::from).toList();
    }
}

The local catch is intentionally small so the read slice returns 404 now. Day 10 centralizes exception formatting with RestControllerAdvice. Do not copy broad catch (Exception) everywhere; it can hide programming defects behind incorrect 400/404 responses.

The collection contract here requires customerId, unlike Day 6's optional filter. That is an intentional exercise version, not an unnoticed compatibility promise. In real deployed code, changing required fields needs an API compatibility decision. Authenticated customer context will later replace trusting this input for access control.

9. Trace one request all the way

GET /api/accounts/101 HTTP/1.1
Accept: application/json
  1. React sends the request; it does not know Java package names.
  2. MVC selects AccountController.get and binds ID 101.
  3. The controller calls AccountService.get(101).
  4. The service calls AccountRepository.findById(101). The injected actual object is InMemoryAccountRepository.
  5. The implementation returns Optional containing an Account with BigDecimal balance.
  6. The service unwraps and returns that domain value.
  7. The controller maps it into AccountResponse and wraps it in 200.
  8. Jackson serializes the response record as JSON.
  9. React parses JSON and updates the balance display.
{"id":101,"type":"SAVINGS","balance":"50000.00","currency":"INR"}

For 999, the repository returns empty Optional, service throws AccountNotFoundException, controller translates it to 404, and React shows not found without parsing an absent JSON body. No SQL or business formatting leaked across layers.

10. Constructor injection and practical IoC

private final AccountService service;

public AccountController(AccountService service) {
    this.service = service;
}

The field says what this controller needs. The constructor says it cannot be constructed correctly without that dependency. Spring resolves the constructor parameter type and supplies a compatible bean. With one constructor, explicit @Autowired is unnecessary in this setup.

At startup, Spring discovers the repository implementation, service, and controller, then resolves their graph. An interface is not an object; the matching implementation bean is the object injected. If two AccountRepository implementations are active without a selection rule, Spring may fail because the dependency is ambiguous. Use profiles, @Primary, or @Qualifier deliberately when multiple implementations are needed.

// Anti-pattern in a managed controller:
private final AccountService service =
    new AccountService(new InMemoryAccountRepository());

This hardcodes storage, bypasses the container-managed collaborator lifecycle, and makes test replacement harder. new is still correct for DTOs/domain values and for deliberately assembling unit tests. The issue is constructing managed dependencies inside their consumers. Later proxies for transactions or other cross-cutting behavior can also be bypassed by unmanaged objects.

Field injection such as @Autowired private AccountService service; hides required dependencies from the constructor and makes plain construction incomplete. Constructor injection is easier to reason about, supports final fields, and enables direct tests.

11. Transfer rules: interface plus service

A transfer needs more than “save an Account.” We illustrate eligibility preview only, so no balances change and no response claims settlement. Actual transfers require transaction boundaries, authorization, audit, idempotency, and concurrency control later.

Create validation/TransactionValidator.java:

package com.example.bank.validation;
import java.math.BigDecimal;

public interface TransactionValidator {
    void validate(BigDecimal amount);
}

Create validation/DailyLimitValidator.java:

package com.example.bank.validation;

import java.math.BigDecimal;
import org.springframework.stereotype.Component;

@Component
public class DailyLimitValidator implements TransactionValidator {
    private static final BigDecimal DEMO_SINGLE_TRANSFER_LIMIT =
        new BigDecimal("100000.00");

    @Override
    public void validate(BigDecimal amount) {
        if (amount == null || amount.signum() <= 0) {
            throw new IllegalArgumentException("Amount must be positive");
        }
        if (amount.compareTo(DEMO_SINGLE_TRANSFER_LIMIT) > 0) {
            throw new IllegalArgumentException("Demo transfer limit exceeded");
        }
    }
}

The class name links to Day 2, but this demonstration checks a single transfer against a threshold; a real daily limit also sums prior usage in a defined timezone/day and handles concurrent transfers. Naming and explanation must not suggest a production daily-limit guarantee from one comparison.

Create dto/TransferPreviewRequest.java and dto/TransferPreviewResponse.java:

package com.example.bank.dto;
import java.math.BigDecimal;
public record TransferPreviewRequest(
    Long fromAccountId, Long toAccountId, BigDecimal amount, String currency) {}

package com.example.bank.dto;
public record TransferPreviewResponse(String status, String message) {}

Create service/TransferService.java:

package com.example.bank.service;

import com.example.bank.domain.Account;
import com.example.bank.dto.TransferPreviewRequest;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.repository.AccountRepository;
import com.example.bank.validation.TransactionValidator;
import org.springframework.stereotype.Service;

@Service
public class TransferService {
    private final AccountRepository accounts;
    private final TransactionValidator validator;

    public TransferService(AccountRepository accounts,
                           TransactionValidator validator) {
        this.accounts = accounts;
        this.validator = validator;
    }

    public void checkEligibility(TransferPreviewRequest request) {
        if (request.fromAccountId() == null || request.toAccountId() == null) {
            throw new IllegalArgumentException("Both account IDs are required");
        }
        if (request.fromAccountId().equals(request.toAccountId())) {
            throw new IllegalArgumentException("Accounts must differ");
        }
        validator.validate(request.amount());
        Account from = accounts.findById(request.fromAccountId())
            .orElseThrow(() -> new AccountNotFoundException(request.fromAccountId()));
        Account to = accounts.findById(request.toAccountId())
            .orElseThrow(() -> new AccountNotFoundException(request.toAccountId()));
        if (!from.active() || !to.active()) {
            throw new IllegalArgumentException("Both accounts must be active");
        }
        if (!from.currency().equals(request.currency())
            || !to.currency().equals(request.currency())) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        if (from.balance().compareTo(request.amount()) < 0) {
            throw new IllegalArgumentException("Insufficient funds");
        }
        // Preview ends here. No debit, credit, or transaction is persisted.
    }
}

The service receives two abstractions, coordinates retrieval and rules, and never returns HTTP status codes. compareTo compares decimal values; equals also considers scale, so 10.0 and 10.00 behave differently under equals. Request DTO dependence is a pragmatic learning shortcut here; larger applications map DTOs into application commands so services remain independent of external contracts.

Create controller/TransferPreviewController.java:

package com.example.bank.controller;

import com.example.bank.dto.TransferPreviewRequest;
import com.example.bank.dto.TransferPreviewResponse;
import com.example.bank.exception.AccountNotFoundException;
import com.example.bank.service.TransferService;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/transfer-previews")
public class TransferPreviewController {
    private final TransferService service;
    public TransferPreviewController(TransferService service) {
        this.service = service;
    }

    @PostMapping
    public ResponseEntity<TransferPreviewResponse> preview(
        @RequestBody TransferPreviewRequest request) {
        try {
            service.checkEligibility(request);
            return ResponseEntity.ok(new TransferPreviewResponse(
                "ELIGIBLE", "Preview only; no funds moved"));
        } catch (AccountNotFoundException ex) {
            return ResponseEntity.notFound().build();
        } catch (IllegalArgumentException ex) {
            return ResponseEntity.badRequest().body(
                new TransferPreviewResponse("REJECTED", ex.getMessage()));
        }
    }
}

No resource is persisted, so the preview returns 200, not 201. It reports current eligibility, not a reservation or guarantee; balances may change immediately afterwards. A real transfer must recheck rules within its protected transaction.

POST /api/transfer-previews HTTP/1.1
Content-Type: application/json

{"fromAccountId":101,"toAccountId":102,"amount":"5000.00","currency":"INR"}

{"status":"ELIGIBLE","message":"Preview only; no funds moved"}

12. Unit-testability without an HTTP server

You can test the service with a fake repository and validator. Plain construction is deliberate here: the test controls collaborators instead of hiding them inside the class.

AccountRepository repository = new InMemoryAccountRepository();
TransactionValidator validator = new DailyLimitValidator();
TransferService service = new TransferService(repository, validator);

service.checkEligibility(new TransferPreviewRequest(
    101L, 102L, new java.math.BigDecimal("5000.00"), "INR"));

This fragment belongs inside a test/method, not at class scope. To isolate rules further, write a fake implementing AccountRepository with only the accounts each test needs. Day 15 introduces JUnit/Mockito systematically. The reason testing is easier now is architectural: required collaborators are visible and replaceable.

13. Anti-patterns and repair

  • Fat controller: extract workflow into a service; keep HTTP translation near the edge.
  • Business logic in repository: put limits/eligibility in services or domain policies; repository handles data.
  • Service returns ResponseEntity: remove HTTP coupling; return a result or raise an application failure.
  • Every class calls new on dependencies: receive managed collaborators through constructors.
  • Field injection: expose required dependencies via constructors.
  • Circular dependency: controller → service → controller usually signals misplaced responsibilities.
  • Interface for every trivial class: add abstractions where substitution/boundaries help; not every class needs one.
  • Two repository beans with no selection: choose intentionally rather than adding random annotations.
  • Service catches every exception and returns success: preserve failure semantics.

14. Why this matters in real work

A bank may change its storage, validation policy, or API representation independently. Layers make those changes local. Interfaces and constructor injection enable service tests before a database exists. Clear boundaries also reveal where transactions, security checks, and observability should eventually wrap a workflow instead of being scattered across endpoints.

Acceptance criteria: the account controller contains no map, the service depends on AccountRepository, repository exposes no HTTP types, constructor injection supplies dependencies, and preview results never claim money moved. Keep missing-account and input failures distinct.

Then design a real daily-limit policy requiring transaction history and an atomic usage update—write the contract, not a misleading single comparison.

16. Knowledge check

1. Which layer chooses 404?

The HTTP/controller layer translates an application not-found outcome to 404. The repository reports absence without knowing HTTP.

2. How does Spring inject an interface?

It injects an actual compatible implementation bean. The interface itself is not instantiated.

3. Does final make repository data immutable?

No. It prevents reassignment of the field reference, not mutation inside the referenced object.

4. Why avoid new AccountService in a managed controller?

It hardcodes assembly, bypasses managed lifecycle/proxy behavior, and makes substitution harder. Constructor injection states the dependency explicitly.

5. Is an ELIGIBLE preview a guaranteed transfer?

No. It observes current state without reserving funds. Actual transfer execution must recheck under transaction/concurrency protection.

6. What is dependency inversion here?

Application behavior depends on a repository/validator contract, while interchangeable concrete implementations provide its behavior.

17. Cheat sheet

Controller = HTTP. Service = application rules/orchestration. Repository = storage contract/adapter. Domain = core values. DTO = API representation. Constructor injection makes dependencies explicit; Spring assembles discovered beans. Depend on useful abstractions, keep request state local, and test services directly. A clean layer diagram does not automatically supply atomic money movement. Next: make input/output contracts explicit and validate them.
