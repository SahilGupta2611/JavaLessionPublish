Quick recap: Class and Object

Suppose we need to represent a bank account.

JAVA
public class BankAccount {

    private String accountNumber;
    private double balance;

    public BankAccount(
            String accountNumber,
            double balance) {

        this.accountNumber = accountNumber;
        this.balance = balance;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

Create an object:

JAVA
BankAccount account =
    new BankAccount("ACC1001", 10000);

account.deposit(5000);

System.out.println(account.getBalance());

Output:

TEXT
15000

Think:

TEXT
BankAccount
    ↓
Class / blueprint

account
    ↓
Object / actual instance

You covered this in Day 1.

FOUNDATIONS / 03

Encapsulation

Notice:

JAVA
private double balance;

instead of:

JAVA
public double balance;

Why?

Because this would be dangerous:

JAVA
account.balance = -500000;

Anyone could modify the balance directly.

Instead:

JAVA
private double balance;

public void deposit(double amount) {

    if (amount <= 0) {
        throw new IllegalArgumentException(
            "Amount must be positive"
        );
    }

    balance += amount;
}

Now the object controls how its data changes.

That's encapsulation.

Think:

Keep data protected and provide controlled operations around it.

For banking systems, this is particularly important.

FOUNDATIONS / 04

Inheritance — extends

Suppose our bank supports:

TEXT
BankAccount
     ↑
 ┌───┴────┐
 ↓        ↓
Savings  Current
Account  Account

Both have:

TEXT
accountNumber
balance
deposit()

We don't want to duplicate everything.

Create a parent:

JAVA
public class BankAccount {

    protected String accountNumber;
    protected double balance;

    public void deposit(double amount) {
        balance += amount;
    }

    public double getBalance() {
        return balance;
    }
}

Then:

JAVA
public class SavingsAccount
        extends BankAccount {

    public void addInterest() {

        balance =
            balance + (balance * 0.04);
    }
}

Important:

JAVA
extends

means inheritance.

TEXT
SavingsAccount
IS-A
BankAccount

Therefore:

JAVA
SavingsAccount account =
    new SavingsAccount();

account.deposit(5000);

works because deposit() comes from BankAccount.

The protected fields demonstrate inheritance. Prefer private state and controlled operations when designing real account models.

Parent:

    @Override

Current:

JAVA
public class CurrentAccount
        extends BankAccount {

    }

@Override means:

I'm replacing/customizing behavior inherited from the parent.

So:

JAVA
SavingsAccount account =
    new SavingsAccount();

System.out.println(

prints:

TEXT
50

CONTRACTS & BEHAVIOR / 07

Interfaces

Imagine our bank supports:

TEXT
UPI
NEFT
IMPS

All of them can transfer money.

We define a contract:

JAVA
public interface PaymentProcessor {

    void transfer(
        String fromAccount,
        String toAccount,
        double amount
    );
}

Notice:

JAVA
interface

An interface essentially says:

Any class claiming to be a PaymentProcessor must provide this behavior.

It describes what must happen.

The implementations decide how.

CONTRACTS & BEHAVIOR / 08

implements

Create a UPI implementation:

JAVA
public class UpiPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void transfer(
            String fromAccount,
            String toAccount,
            double amount) {

        System.out.println(
            "UPI transfer ₹" + amount
        );
    }
}

Create NEFT:

JAVA
public class NeftPaymentProcessor
        implements PaymentProcessor {

    @Override
    public void transfer(
            String fromAccount,
            String toAccount,
            double amount) {

        System.out.println(
            "NEFT transfer ₹" + amount
        );
    }
}

The relationship is:

TEXT
PaymentProcessor
       ↑
       │ implements
 ┌─────┴──────┐
 ↓            ↓
UPI          NEFT

Both classes satisfy the same contract.

CONTRACTS & BEHAVIOR / 10

Polymorphism

Now look carefully:

JAVA

    new UpiPaymentProcessor();

Left:

JAVA
PaymentProcessor

Right:

JAVA
UpiPaymentProcessor

This is perfectly valid.

We can later change:

JAVA

    new NeftPaymentProcessor();

Our variable still works with a PaymentProcessor.

This is polymorphism.

Think:

One interface, multiple possible implementations.
TEXT
          PaymentProcessor
               ↑
       ┌───────┼───────┐
       │       │       │

CONTRACTS & BEHAVIOR / 11

Why polymorphism matters

Suppose we write:

JAVA
public class TransferService {

    private UpiPaymentProcessor processor;
}

Our service is tied specifically to:

TEXT
UPI

Tomorrow the bank says:

Use NEFT.

Now our service needs changing.

Instead:

JAVA
public class TransferService {

    private PaymentProcessor processor;
}

Now:

TEXT

      ↓
PaymentProcessor
      ↓
any implementation

The service doesn't care whether it's:

TEXT
UPI
NEFT
IMPS

That's flexible design.

CONTRACTS & BEHAVIOR / 12

THE BANKING SERVICE / 16

Our main Day 2 banking example

Let's create a transaction-validation system.

Business rule:

Transfers above ₹1,00,000 should be rejected.

Instead of putting the rule directly inside TransferService, create an interface.

JAVA
public interface TransactionValidator {

    boolean isValid(double amount);
}

This says:

Any transaction validator must be able to validate an amount.
THE BANKING SERVICE / 17

Implementation

JAVA
public class DailyLimitValidator
        implements TransactionValidator {

    @Override
    public boolean isValid(double amount) {

        return amount <= 100000;
    }
}

Therefore:

TEXT
₹50,000
↓
true


₹1,50,000
↓
false
This lesson’s DailyLimitValidator checks one amount against a cap. A cumulative daily limit also needs the customer’s total for the day. The exercise adds a positive-amount check.
THE BANKING SERVICE / 18

TransferService

Now:

JAVA
public class TransferService {

    private final TransactionValidator validator;

    public TransferService(
            TransactionValidator validator) {

        this.validator = validator;
    }

    public void transfer(double amount) {

        if (!validator.isValid(amount)) {

            System.out.println(
                "Transfer rejected"
            );

            return;
        }

        System.out.println(

JAVA
private final TransactionValidator validator;

THE BANKING SERVICE / 19

THE BANKING SERVICE / 23

You saw:

JAVA

Why final?

Because after the constructor assigns:

JAVA

we don't want someone replacing that reference later:

JAVA

For Spring services, constructor-injected dependencies are commonly held as final.

Full runnable example

Save the four public types as TransactionValidator.java, DailyLimitValidator.java, TransferService.java, and Main.java in the same folder. Other lesson examples are separate alternatives.

BUILD & REVIEW / 29

Quick knowledge check

Try answering these before revealing each answer. Explain the idea in your own words.

1. What does extends mean?

Inheritance.

JAVA
SavingsAccount extends BankAccount
2. What does implements mean?

A class provides the behavior required by an interface.

JAVA
DailyLimitValidator
    implements TransactionValidator
3. What's an interface?

A contract describing behavior that implementations must provide.

4. What's polymorphism?

One abstraction/interface can represent different implementations.

JAVA
TransactionValidator validator =
    new DailyLimitValidator();

could later become:

JAVA
TransactionValidator validator =
    new MinimumAmountValidator();
5. What's abstraction?

Expose necessary behavior while hiding unnecessary implementation details.

6. What's inheritance?

A child class inherits behavior/state from a parent:

JAVA
SavingsAccount
    extends BankAccount
7. What's dependency injection in simple terms?

Instead of the service creating its dependency, someone supplies it from outside, typically through the constructor. In a Spring Boot application, Spring can supply it.

8. What does final mean for an injected dependency?

The field reference cannot be reassigned after it is initialized. It does not make the referenced object immutable.

BUILD & REVIEW / 30

Day 2 cheat sheet

Class → blueprint for objects.

Object → an actual instance created with new.

Encapsulation → protect state and control changes through methods.

**extends** → inheritance: a child class is a kind of its parent.

**@Override** → a method implements or overrides an inherited method; the compiler checks the signature.

Interface → contract: what behavior a collaborator provides.

**implements** → a class provides an interface's required behavior.

Implementation → concrete class: how that behavior works.

Polymorphism → one abstraction, different implementations; the actual object's method runs.

Abstraction → expose necessary operations and hide unnecessary implementation details.

Abstract class → shared base state/behavior, with optional abstract methods.

Constructor injection → dependencies arrive through the constructor.

**final dependency** → keep the same field reference after construction.

JAVA
private final TransactionValidator validator;

public TransferService(TransactionValidator validator) {
    this.validator = validator;
}

The central pattern: depend on the contract, receive the implementation, and delegate the behavior.
