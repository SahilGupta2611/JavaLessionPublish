01 / THE ARCHITECTURE

One transfer. Three roles.

The service performs the operation. The interface defines the validation contract. The implementation supplies a concrete rule.

BUSINESS OPERATIONTransferService“Can I transfer this amount?”

↓ depends on

CONTRACT · INTERFACETransactionValidatorboolean isValid(double amount)

↑ implements

CONCRETE RULEDailyLimitValidatorAccept amounts up to ₹1,00,000
At runtime, the service calls the actual validator object through the interface reference.
02 / INTERFACE

Write the contract first.

An interface describes what a collaborator can do. It lets the service request validation without knowing the rule’s details.

public interface TransactionValidator {
    boolean isValid(double amount);
}

The promise

Receive an amount and return true or false.

The abstraction

The caller sees the capability, while the validation logic lives behind the contract.

03 / IMPLEMENTS

Give the contract a rule.

implements means this class provides the behavior required by the interface. @Override helps the compiler check that the method matches.

public class DailyLimitValidator
        implements TransactionValidator {

    @Override
    public boolean isValid(double amount) {
        return amount <= 100000;
    }
}
Teaching simplification: this checks a single amount against a cap. A real daily limit must also track the customer’s total transfers for the day. This example accepts zero and negative amounts; production validation must reject them.
04 / CONSTRUCTOR INJECTION

Pass the dependency in.

The constructor receives a validator. The service stores it and delegates the validation decision to it.

public class TransferService {
    private final TransactionValidator validator;

    public TransferService(TransactionValidator validator) {
        this.validator = validator;
    }

    public void transfer(double amount) {
        if (!validator.isValid(amount)) {
            System.out.println("Transfer rejected");
            return;
        }
        System.out.println("Transfer successful");
    }
}

final prevents reassignment of the field after construction. It does not make the validator object immutable.

05 / THE BIG IDEA

Depend on the capability.

FLEXIBLE DEPENDENCY
private final
    TransactionValidator validator;

Any implementation of the interface can be supplied.

SPECIFIC DEPENDENCY
private final
    DailyLimitValidator validator;

The service is tied to this concrete class (or its subclasses).

Polymorphism: the reference type is TransactionValidator, but the object can be a DailyLimitValidator. Java dispatches the method call to the object’s implementation.

Why it matters: swap in another validator or a test double without changing the transfer method. This is the practical value of abstraction and depending on an interface.
06 / RUN IT

Wire it. Try two transfers.

This plain Java entry point connects the objects manually. Save each public type in its matching .java file in the same folder.

public class Main {
    public static void main(String[] args) {
        TransactionValidator validator =
                new DailyLimitValidator();
        TransferService service = new TransferService(validator);

        service.transfer(50000);   // ₹50,000: succeeds
        service.transfer(150000);  // ₹1,50,000: rejected
    }
}
EXPECTED CONSOLE OUTPUT
Transfer successful
Transfer rejected

Compile: javac *.java · Run: java Main. These messages demonstrate validation; they do not move real money.

07 / SPRING BOOT CONNECTION

Same design. Spring wires it.

Constructor injection works without Spring. In a Spring Boot application, Spring can create and connect the objects for you.

// DailyLimitValidator.java
import org.springframework.stereotype.Component;

@Component
public class DailyLimitValidator implements TransactionValidator {
    @Override
    public boolean isValid(double amount) {
        return amount <= 100000;
    }
}

// TransferService.java — add this to the service above:
// import org.springframework.stereotype.Service;
// @Service
Keep the service constructor unchanged. With a single constructor, no @Autowired is needed. Both classes must be discovered by component scanning. If multiple validator beans exist, choose one with @Qualifier or @Primary.
08 / YOUR TURN

Make the rule replaceable.

  1. Create the interface, validator, service and Main from the previous slides.
  2. Run ₹50,000 and ₹1,50,000. Check the expected messages.
  3. Add PositiveAmountValidator implementing the same interface. Its rule: amount > 0.
  4. Inject the new validator into the existing service. Try -100, 0 and 150000.
Predict first: ₹1,50,000 now succeeds because you replaced the cap rule with the positive-amount rule. Multiple rules require combining validators.
Reveal the replacement
public class PositiveAmountValidator implements TransactionValidator {
    @Override
    public boolean isValid(double amount) {
        return amount > 0;
    }
}

// In Main:
TransferService service =
    new TransferService(new PositiveAmountValidator());

For real currency, use BigDecimal or integer minor units instead of double.

10 / WRAP UP

A contract keeps options open.

“TransferService needs something that can validate a transaction. It doesn’t need to own a particular validation rule.”

Interface + abstraction

Define the capability and hide the rule’s details.

Implements + polymorphism

Provide the rule and call it through the common contract.

Constructor injection

Receive the collaborator from outside the service.
