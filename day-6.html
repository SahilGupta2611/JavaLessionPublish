Your destination today

Build typed, predictable GET endpoints for accounts, customers, and transactions. Explain routing annotations, path and query binding, JSON responses, and ResponseEntity. Understand where a controller's responsibility ends. Allow 2–3 hours with the lab.

Prerequisites: a running Java 21 / Spring Boot 3.5 banking skeleton from Day 5, plus Day 4 methods/status codes and Day 3 List/Optional. We still use sample data. There is no database or authentication implementation; endpoint IDs are not permission checks.

1. The controller is an HTTP adapter

A React component should not implement the bank's ledger. Similarly, a controller should not own every banking rule. Its job is to accept HTTP input, call application behavior, and translate the result into an HTTP response.

GET /api/accounts/101
    → Spring MVC selects controller method
    → converts "101" to Long
    → method retrieves a result
    → response converter serializes Java value
    → 200 + JSON back to React

Spring MVC uses a dispatcher to route requests. You register mappings with annotations. The method name get has no special routing power; the annotation's method/path combination selects it. Many requests can call the same controller instance concurrently, so avoid request-specific mutable fields.

2. @RestController, deeply explained

@RestController combines controller registration with response-body behavior. Spring discovers the class under the root package and treats returned values as HTTP bodies. A plain @Controller is commonly used for server-rendered views; without response-body behavior, a returned string may be interpreted as a view name. A REST controller returning a string returns text, while returning a record/map/list normally produces JSON when the JSON converter is available.

@RestController
@RequestMapping("/api/accounts")
public class AccountController {
    @GetMapping("/{id}")
    public AccountResponse get(@PathVariable("id") Long id) {
        return new AccountResponse(id, "SAVINGS", "50000.00", "INR");
    }
}

This is a focused fragment; imports and a complete implementation follow below. @RequestMapping on the class provides the shared URL prefix. @GetMapping narrows the method to GET and adds the suffix. Together they match /api/accounts/101. @PathVariable("id") explicitly matches the placeholder, then Spring converts text to Long. Naming explicitly avoids relying on compiler parameter-name metadata.

The example initially echoes any ID; that is useful for binding practice but not correct account lookup. The complete version returns 404 when the requested sample account does not exist.

3. Java values become JSON through Jackson

Create domain/AccountResponse.java under com.example.bank for today's read-model practice (Day 9 moves API models into dto):

package com.example.bank.domain;

public record AccountResponse(
    Long id, Long customerId, String type,
    String balance, String currency) {}

A record gives a constructor and accessors such as id() and balance(). In Boot 3's web setup Jackson reads the record components and writes JSON. It is not calling React and it is not returning JavaScript source.

{
  "id": 101,
  "customerId": 7,
  "type": "SAVINGS",
  "balance": "50000.00",
  "currency": "INR"
}

A List<AccountResponse> becomes a JSON array. Java property names influence the contract. Renaming customerId to owner changes what React receives unless you deliberately preserve mapping. Dates, enums, and money need documented formats. We use decimal strings for money responses and BigDecimal for arithmetic in later lessons. Do not build JSON by string concatenation: escaping and types are error-prone.

4. Complete account read controller

Each public type goes in its own file. This is a self-contained read example; remove conflicting Day 5 practice account routes if you added any. Keep BankInfoController.

package com.example.bank.controller;

import com.example.bank.domain.AccountResponse;
import java.util.List;
import java.util.Map;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/accounts")
public class AccountController {
    private final Map<Long, AccountResponse> samples = Map.of(
        101L, new AccountResponse(101L, 7L, "SAVINGS", "50000.00", "INR"),
        102L, new AccountResponse(102L, 7L, "CURRENT", "20000.00", "INR"),
        103L, new AccountResponse(103L, 8L, "SAVINGS", "8000.00", "INR")
    );

    @GetMapping("/{id}")
    public ResponseEntity<AccountResponse> get(@PathVariable("id") Long id) {
        AccountResponse account = samples.get(id);
        if (account == null) {
            return ResponseEntity.notFound().build();
        }
        return ResponseEntity.ok()
            .header("Cache-Control", "no-store")
            .body(account);
    }

    @GetMapping
    public List<AccountResponse> list(
        @RequestParam(name = "type", required = false) String type,
        @RequestParam(name = "customerId", required = false) Long customerId) {
        return samples.values().stream()
            .filter(a -> type == null || a.type().equalsIgnoreCase(type))
            .filter(a -> customerId == null || a.customerId().equals(customerId))
            .sorted(java.util.Comparator.comparing(AccountResponse::id))
            .toList();
    }
}

The samples field is fixed and immutable; it deliberately contains only learning data. Each request's parameters stay local. Map.get returns null when absent. notFound().build() produces 404 with no body here. ok().header(...).body(account) constructs a 200 response including a header and typed body.

@GetMapping without a suffix maps the collection path. required=false allows a missing filter, bound as null. A boxed Long can represent absence; primitive long cannot. The stream starts from all sample values, keeps matches, sorts by ID for deterministic output, and creates a list. An empty collection result is 200 [], not automatically 404.

This filtering accepts arbitrary type strings and produces an empty list when they do not match. If your contract requires invalid enum filters to produce 400, bind an enum or validate explicitly. Make that choice deliberate.

5. Path variables versus query parameters

GET /api/accounts/101                    → get(id=101)
GET /api/accounts?type=SAVINGS           → list(type="SAVINGS", customerId=null)
GET /api/accounts?customerId=7&type=CURRENT → list(type="CURRENT", customerId=7)
GET /api/accounts/not-a-number           → conversion error, normally 400
GET /api/accounts/999                    → sample not present, 404

The first uses identity; the next two refine a collection. Conversion errors happen before your method body can perform a lookup. Missing a required query parameter is also a request error. A missing optional value is different from an empty value: ?type= is present with an empty string and your API must decide whether to reject or treat it as absent.

Do not accept account ownership merely because customerId=7 was supplied. A malicious caller can change a query parameter. Later security derives the customer identity from authenticated context and checks access.

6. Defaults and optional parameters

@GetMapping("/preview")
public ResponseEntity<List<AccountResponse>> preview(
    @RequestParam(name = "limit", defaultValue = "2") int limit) {
    if (limit < 1 || limit > 20) {
        return ResponseEntity.badRequest().build();
    }
    return ResponseEntity.ok(samples.values().stream()
        .sorted(java.util.Comparator.comparing(AccountResponse::id))
        .limit(limit).toList());
}

Add this method inside AccountController. defaultValue="2" supplies a fallback for a missing or empty parameter. Spring converts it to int. Explicit range checking prevents negative stream limits and excessive responses. This is a small preview limit, not database pagination; page/size with Spring Data comes on Day 14.

Spring can also bind Optional<String> query parameters, but null with an explicit required=false is sufficient here. Choose one convention. Do not mistake Optional for validation: Optional.of("invalid") is still invalid input.

7. Customer and nested transaction examples

Create domain/CustomerResponse.java:

package com.example.bank.domain;
public record CustomerResponse(Long id, String name) {}

Create controller/CustomerController.java:

package com.example.bank.controller;

import com.example.bank.domain.CustomerResponse;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/customers")
public class CustomerController {
    @GetMapping("/{id}")
    public ResponseEntity<CustomerResponse> get(@PathVariable("id") Long id) {
        if (!id.equals(7L)) return ResponseEntity.notFound().build();
        return ResponseEntity.ok(new CustomerResponse(7L, "Asha Rao"));
    }
}

Wildcard imports are used here to keep the small example readable; your IDE can expand them. The response intentionally contains a profile summary, not passwords or identity documents.

Create domain/TransactionResponse.java:

package com.example.bank.domain;
public record TransactionResponse(
    Long id, Long accountId, String type, String amount) {}

Create controller/TransactionController.java:

package com.example.bank.controller;

import com.example.bank.domain.TransactionResponse;
import java.util.List;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/accounts/{accountId}/transactions")
public class TransactionController {
    @GetMapping
    public ResponseEntity<List<TransactionResponse>> list(
        @PathVariable("accountId") Long accountId,
        @RequestParam(name = "type", required = false) String type) {
        if (!accountId.equals(101L)) return ResponseEntity.notFound().build();
        List<TransactionResponse> transactions = List.of(
            new TransactionResponse(3001L, 101L, "DEBIT", "500.00"),
            new TransactionResponse(3002L, 101L, "CREDIT", "1000.00")
        );
        return ResponseEntity.ok(transactions.stream()
            .filter(t -> type == null || t.type().equalsIgnoreCase(type))
            .toList());
    }
}

The nested path communicates “transactions belonging to this account.” This controller's practice fixture has only account 101; the lab extends it. Returning 404 for an unknown parent is different from returning an empty list for a known account with no matching transactions. A future /api/transactions/{id} lookup must also verify ownership rather than expose any globally known transaction.

8. ResponseEntity is the whole response envelope

Returning AccountResponse directly normally yields 200 and converter-selected headers. Returning ResponseEntity<AccountResponse> lets you explicitly choose status, headers, and body. Generic type AccountResponse describes the body type, not the status.

ResponseEntity.ok(account);                 // 200 with body
ResponseEntity.notFound().build();          // 404, no body here
ResponseEntity.badRequest().build();        // 400, no body here
ResponseEntity.noContent().build();         // 204, no body

These are usage fragments, not statements to paste at class scope. ResponseEntity is immutable after construction. Do not manually return an HTTP status line as a string: that would be text in a body, not the actual status. A custom response header must be meaningful; inventing X-Success: true is redundant with a successful status.

9. Test the contract from outside Java

curl -i http://localhost:8080/api/accounts/101
curl -i 'http://localhost:8080/api/accounts?customerId=7&type=SAVINGS'
curl -i 'http://localhost:8080/api/accounts/preview?limit=1'
curl -i 'http://localhost:8080/api/accounts/101/transactions?type=DEBIT'
curl -i http://localhost:8080/api/accounts/999

Quote URLs containing & in your shell. In Postman, choose GET, enter the URL, use its Params table for filters, then inspect status, headers, and body separately. No request JSON body is needed for these GETs.

async function loadAccounts(customerId, type) {
  const params = new URLSearchParams({ customerId: String(customerId) });
  if (type) params.set("type", type);
  const response = await fetch(`/api/accounts?${params}`);
  if (!response.ok) throw new Error(`Accounts failed: ${response.status}`);
  return response.json();
}

React receives an array, so map it to cards with stable account.id keys. Use loading/error state while the promise is pending. With separate localhost ports, use your React dev proxy or configured backend origin. A CORS issue is not fixed by renaming a Java method.

async function loadAccount(id) {
  const response = await fetch(`/api/accounts/${encodeURIComponent(id)}`);
  if (response.status === 404) return null;
  if (!response.ok) throw new Error(`Account failed: ${response.status}`);
  return response.json();
}

This function avoids parsing the empty 404 from our example. Returning null is a client convention you choose; the server's contract remains a 404 response.

10. What belongs in a controller?

Belongs here: method/path mapping, HTTP input binding, validation entry points, invoking a service, choosing status and safe response fields. Does not belong here: implementing interest calculations, daily transfer limits, ledger updates, SQL, or durable retry handling.

Our sample maps are intentionally a temporary teaching shortcut. Day 8 removes data access and business logic from controllers. The progression lets you understand routing first instead of hiding it behind unfamiliar layers. A controller should normally delegate to a service and remain readable enough that a reviewer can see the endpoint contract at a glance.

11. Common mistakes and diagnoses

  • Returning a JSON string: use a typed record; otherwise escaping and Content-Type can surprise clients.
  • Wrong placeholder name: /accounts/{id} must match @PathVariable("id").
  • Two identical GET mappings: startup can fail with an ambiguous mapping. Rename a route or consolidate methods.
  • Optional primitive query field: use a boxed type, Optional, or default value when absence is meaningful.
  • Missing converter/dependency: verify the web starter and compatible Boot baseline before writing manual JSON.
  • Everything returns 200: an unknown individual resource should use an appropriate error status.
  • 404 for every empty list: a collection can validly be empty.
  • Controller stores request state: shared fields can mix users across requests.
  • Adding broad @CrossOrigin as a security fix: CORS and authentication solve different problems.

12. Why this matters in backend work

Controllers are where frontend expectations meet Java types. Explicit binding and consistent responses prevent integration surprises. Correct empty/not-found behavior helps the UI choose between “no transactions yet” and “account does not exist.” Small HTTP adapters also make later architecture refactoring possible without changing public URLs.

14. Knowledge check

1. Does the Java method name determine the URL?

No. Mapping annotations determine the route and method. The method could be named differently without changing the HTTP contract.

2. What does RestController do to a returned record?

It makes the return value a response body; a JSON message converter serializes its components into JSON.

3. What is the difference between a missing account and an empty transaction list?

A missing individual/parent account can return 404. A known account with zero matching transactions returns a successful empty collection.

4. Why use ResponseEntity?

It lets a method choose actual HTTP status, response headers, and typed body together.

5. Why is required=false alone unsuitable for a primitive Long alternative, long?

A missing value needs a representable absence. A primitive cannot be null; use a default or boxed/optional type.

6. Is customerId supplied in a query proof of identity?

No. It is untrusted client input. The server must enforce permissions using authenticated identity.

15. Cheat sheet

@RestController = HTTP adapter with response-body semantics. Class @RequestMapping + method @GetMapping = full route. @PathVariable binds identity; @RequestParam binds retrieval options. Record/list → converter → JSON. ResponseEntity controls the envelope. Keep request state local. Next: create and change resources with POST, PUT, PATCH, and DELETE.
