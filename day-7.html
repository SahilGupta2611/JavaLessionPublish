Your destination today

Implement a complete practice CRUD API, then explain how financial operations differ from ordinary profile changes. You will bind JSON with RequestBody, generate IDs, return 201 with Location, distinguish replacement from partial update, and handle deletion/conflicts. Allow 3–4 hours with the lab.

Prerequisites: Days 4–6 HTTP, Spring startup, records, controllers, and ResponseEntity; Day 3 Map and Optional. Use the Java 21 / Boot 3.5 baseline. No database, authentication, or money movement is implemented by the CRUD example. Keep it on your learning machine with fictional data.

1. From reading data to accepting commands

GET answers a question. POST/PUT/PATCH/DELETE ask the server to change state. These endpoints must be more careful because an incorrect write can outlive the UI that sent it.

React form → JSON.stringify → POST + Content-Type
    → Spring reads body → Jackson creates request value
    → method checks input/current state → store changes
    → ResponseEntity → JSON result → React updates screen

@RequestBody tells Spring to read the request body through a message converter. It does not mean “read URL parameters.” A malformed JSON body fails during parsing before your method runs. Valid JSON can still contain invalid values. Day 9 adds declarative validation; today's code performs small explicit checks so the exercise is usable now.

2. Select a safe practice resource: beneficiaries

A beneficiary is a customer's saved payee. Creating, renaming, and deleting a saved payee teaches CRUD without pretending arbitrary balance edits are legitimate banking operations. Our simplified fields are name and destinationAccount; later a real system verifies destination ownership/eligibility and controls approval workflows.

Operation Route Input Success
Create POST /api/customers/7/beneficiaries name + destinationAccount 201 + Location
List GET same collection none 200 array
Read GET .../beneficiaries/1 ID 200 object
Replace PUT .../beneficiaries/1 all writable fields 200 object
Rename PATCH .../beneficiaries/1 name only 200 object
Remove DELETE .../beneficiaries/1 ID 204

The parent customer must exist. This exercise supports only customer 7. The URL is not authentication; a real service must verify that the caller may manage that customer's beneficiaries.

3. The model and request contract

Create domain/Beneficiary.java:

package com.example.bank.domain;

public record Beneficiary(
    Long id, Long customerId, String name, String destinationAccount) {}

Create dto/BeneficiaryRequest.java:

package com.example.bank.dto;

public record BeneficiaryRequest(String name, String destinationAccount) {}

Create dto/RenameBeneficiaryRequest.java:

package com.example.bank.dto;

public record RenameBeneficiaryRequest(String name) {}

The server owns id and customerId; they do not come from the create payload. Separating these fields already limits accidental over-posting. The rename request has one allowed change. We return the domain record directly in this introductory example because its fields are deliberately safe; Day 9 formalizes separate response DTOs.

4. Complete in-memory store

Create repository/BeneficiaryStore.java. This is a practice store bean, not Spring Data JPA. It loses all records when the process restarts and is not shared across multiple application instances.

package com.example.bank.repository;

import com.example.bank.domain.Beneficiary;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Repository;

@Repository
public class BeneficiaryStore {
    private final Map<Long, Beneficiary> data = new HashMap<>();
    private long nextId = 1;

    public synchronized List<Beneficiary> list(Long customerId) {
        return data.values().stream()
            .filter(b -> b.customerId().equals(customerId))
            .sorted(java.util.Comparator.comparing(Beneficiary::id))
            .toList();
    }

    public synchronized Optional<Beneficiary> find(Long customerId, Long id) {
        return Optional.ofNullable(data.get(id))
            .filter(b -> b.customerId().equals(customerId));
    }

    public synchronized Optional<Beneficiary> create(
        Long customerId, String name, String destinationAccount) {
        if (duplicate(customerId, destinationAccount, null)) return Optional.empty();
        Long id = nextId++;
        Beneficiary b = new Beneficiary(id, customerId, name, destinationAccount);
        data.put(id, b);
        return Optional.of(b);
    }

    public synchronized boolean duplicate(
        Long customerId, String destinationAccount, Long excludingId) {
        return data.values().stream().anyMatch(b ->
            b.customerId().equals(customerId)
            && b.destinationAccount().equals(destinationAccount)
            && !b.id().equals(excludingId));
    }

    public synchronized void save(Beneficiary beneficiary) {
        data.put(beneficiary.id(), beneficiary);
    }

    public synchronized void delete(Long id) {
        data.remove(id);
    }
}

@Repository makes this a discoverable data-access collaborator. nextId++ allocates a server ID and advances the counter. synchronized protects each method's access to the HashMap/counter within one JVM. It does not create a database transaction or guarantee multi-method business atomicity. find filters on customer as well as ID, avoiding retrieval under the wrong parent. Optional expresses absence without a null result leaking to callers.

duplicate excludes the current ID during update, so saving an unchanged destination is allowed. create checks duplicates and inserts under one lock. The controller below also holds the same store lock for its read/check/write update sequence. This deliberately simple synchronization keeps the lab deterministic; Day 8 moves orchestration to a service, and later database constraints/transactions provide durable guarantees.

5. Complete CRUD controller

Create controller/BeneficiaryController.java:

package com.example.bank.controller;

import com.example.bank.domain.Beneficiary;
import com.example.bank.dto.BeneficiaryRequest;
import com.example.bank.dto.RenameBeneficiaryRequest;
import com.example.bank.repository.BeneficiaryStore;
import java.net.URI;
import java.util.List;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/customers/{customerId}/beneficiaries")
public class BeneficiaryController {
    private final BeneficiaryStore store;

    public BeneficiaryController(BeneficiaryStore store) {
        this.store = store;
    }

    private boolean knownCustomer(Long id) { return id.equals(7L); }
    private boolean blank(String value) { return value == null || value.isBlank(); }

    @GetMapping
    public ResponseEntity<List<Beneficiary>> list(
        @PathVariable("customerId") Long customerId) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        return ResponseEntity.ok(store.list(customerId));
    }

    @GetMapping("/{id}")
    public ResponseEntity<Beneficiary> get(
        @PathVariable("customerId") Long customerId,
        @PathVariable("id") Long id) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        return store.find(customerId, id).map(ResponseEntity::ok)
            .orElseGet(() -> ResponseEntity.notFound().build());
    }

    @PostMapping
    public ResponseEntity<Beneficiary> create(
        @PathVariable("customerId") Long customerId,
        @RequestBody BeneficiaryRequest request) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        if (blank(request.name()) || blank(request.destinationAccount())) {
            return ResponseEntity.badRequest().build();
        }
        var created = store.create(customerId, request.name().trim(),
                                   request.destinationAccount().trim());
        if (created.isEmpty()) {
            return ResponseEntity.status(HttpStatus.CONFLICT).build();
        }
        Beneficiary b = created.get();
        URI location = URI.create("/api/customers/" + customerId
            + "/beneficiaries/" + b.id());
        return ResponseEntity.created(location).body(b);
    }

    @PutMapping("/{id}")
    public ResponseEntity<Beneficiary> replace(
        @PathVariable("customerId") Long customerId,
        @PathVariable("id") Long id,
        @RequestBody BeneficiaryRequest request) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        if (blank(request.name()) || blank(request.destinationAccount())) {
            return ResponseEntity.badRequest().build();
        }
        synchronized (store) {
            if (store.find(customerId, id).isEmpty()) {
                return ResponseEntity.notFound().build();
            }
            String destination = request.destinationAccount().trim();
            if (store.duplicate(customerId, destination, id)) {
                return ResponseEntity.status(HttpStatus.CONFLICT).build();
            }
            Beneficiary b = new Beneficiary(id, customerId,
                request.name().trim(), destination);
            store.save(b);
            return ResponseEntity.ok(b);
        }
    }

    @PatchMapping("/{id}")
    public ResponseEntity<Beneficiary> rename(
        @PathVariable("customerId") Long customerId,
        @PathVariable("id") Long id,
        @RequestBody RenameBeneficiaryRequest request) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        if (blank(request.name())) return ResponseEntity.badRequest().build();
        synchronized (store) {
            var existing = store.find(customerId, id);
            if (existing.isEmpty()) return ResponseEntity.notFound().build();
            Beneficiary old = existing.get();
            Beneficiary b = new Beneficiary(id, customerId,
                request.name().trim(), old.destinationAccount());
            store.save(b);
            return ResponseEntity.ok(b);
        }
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> delete(
        @PathVariable("customerId") Long customerId,
        @PathVariable("id") Long id) {
        if (!knownCustomer(customerId)) return ResponseEntity.notFound().build();
        synchronized (store) {
            if (store.find(customerId, id).isEmpty()) {
                return ResponseEntity.notFound().build();
            }
            store.delete(id);
            return ResponseEntity.noContent().build();
        }
    }
}

The constructor receives the store bean; Spring supplies it. We keep explicit checks here so you can see every status decision. This controller is intentionally too large for long-term design; Day 8 introduces a service to own these workflows. Locks in HTTP code are also a teaching compromise, not our destination architecture.

6. Read POST line by line

@PostMapping selects creation requests to the collection. Path binding determines the parent customer. @RequestBody deserializes JSON into BeneficiaryRequest. We check parent existence before attempting insertion, then require nonblank fields. Trimming normalizes surrounding whitespace for this practice contract.

store.create allocates the ID only on successful insertion. An empty Optional indicates duplicate destination, translated to 409. URI.create builds a relative resource URI. ResponseEntity.created(location) sets 201 and the Location header. .body(b) includes the created representation so React can add it to the list immediately.

POST /api/customers/7/beneficiaries HTTP/1.1
Content-Type: application/json

{"name":"Asha Savings","destinationAccount":"ACC102"}

HTTP/1.1 201 Created
Location: /api/customers/7/beneficiaries/1
Content-Type: application/json

{"id":1,"customerId":7,"name":"Asha Savings","destinationAccount":"ACC102"}

Sending the same destination again returns 409 with no body in this implementation. Error JSON is not invented here; Day 10 will standardize error responses. A client must handle empty error bodies as well as JSON.

7. PUT versus PATCH, precisely

Our PUT replaces all writable fields (name, destinationAccount) of an existing beneficiary. It preserves server-owned identity fields. It requires both writable fields, so {"name":"New name"} returns 400 instead of silently preserving an omitted destination. We choose 404 for a missing target rather than supporting create-by-PUT; that is an explicit contract.

PUT /api/customers/7/beneficiaries/1 HTTP/1.1
Content-Type: application/json

{"name":"Home Savings","destinationAccount":"ACC102"}

Our PATCH supports one operation: rename. It requires name, rejects null/blank, and preserves destination. This is a documented custom partial-update contract using JSON, not RFC JSON Patch or JSON Merge Patch. A nullable record alone cannot distinguish omitted and explicit null fields; here both are invalid, so ambiguity is avoided.

PATCH /api/customers/7/beneficiaries/1 HTTP/1.1
Content-Type: application/json

{"name":"Emergency Fund"}

Both return 200 with the updated representation. Repeating this PUT or this rename PATCH has the same intended effect. A future increment-based PATCH would have different retry semantics. Document each patch operation rather than assuming all PATCH requests are idempotent.

8. DELETE and 204

Our DELETE checks parent membership, removes the record, then returns 204 with no body. A second DELETE returns 404, still leaving the resource absent. Deleting a payee record is distinct from deleting a bank account or erasing transaction history. Real account closure may require zero balance and preserve audit data.

async function removeBeneficiary(id) {
  const response = await fetch(`/api/customers/7/beneficiaries/${id}`, {
    method: "DELETE"
  });
  if (!response.ok) throw new Error(`Delete failed: ${response.status}`);
  // 204: update UI state; no JSON body to parse.
}

9. Calling write endpoints from React and curl

async function saveBeneficiary(draft) {
  const response = await fetch("/api/customers/7/beneficiaries", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(draft)
  });
  if (response.status === 409) throw new Error("That payee is already saved");
  if (!response.ok) throw new Error(`Save failed: ${response.status}`);
  return response.json();
}

Disable the submit button while pending for usability, but keep server duplicate checks. On success append the returned record rather than making up an ID in the browser. For PUT send both writable fields; for the custom PATCH send only the rename field.

curl -i -X POST http://localhost:8080/api/customers/7/beneficiaries \
  -H 'Content-Type: application/json' \
  -d '{"name":"Asha Savings","destinationAccount":"ACC102"}'

curl -i -X PATCH http://localhost:8080/api/customers/7/beneficiaries/1 \
  -H 'Content-Type: application/json' -d '{"name":"Emergency Fund"}'

curl -i -X DELETE http://localhost:8080/api/customers/7/beneficiaries/1

Postman uses the same method, URL, header, and raw JSON body. Inspect Location after creation. Paste it into a GET to verify the newly created resource.

10. Accounts, customers, and transfer initiation

Creation contracts differ by resource. POST /api/customers might accept name/email; POST /api/accounts might accept customerId/type/currency. The server assigns IDs, opening policy, and initial balance. It must not accept isAdmin, approved, or arbitrary opening funds because a browser supplied them.

{"customerId":7,"type":"SAVINGS","currency":"INR"}

A transfer is a command creating a financial workflow:

POST /api/transfers HTTP/1.1
Content-Type: application/json

{"fromAccountId":101,"toAccountId":102,"amount":"5000.00","currency":"INR"}

The service must authenticate ownership, check account eligibility/currency, reject identical accounts and nonpositive amounts, check limits and available funds, record the operation, and coordinate debit/credit. Day 8 illustrates rule coordination; Day 13 adds transactions and atomicity. Do not implement it as PUT /accounts/101 {"balance":"45000"}: that lets the client dictate bank state and does not guarantee corresponding credit, audit history, or retry safety.

A real transfer service needs durable idempotency, transaction boundaries, concurrency control, and reconciliation. The CRUD store above does not supply these properties. Calling an endpoint “banking” does not make the toy store financially correct.

11. Why this matters in real work

A write API is an agreement about permitted changes. Server-generated IDs, explicit replacement semantics, documented partial updates, and correct statuses make clients predictable. Duplicate checks belong on the server, eventually backed by durable constraints. Clear contracts allow the UI to recover without guessing whether a resource was created or changed.

12. Common mistakes clinic

  • Returning 200 for creation without a reason: use 201 and Location for a created resource.
  • Trusting IDs/balances from payloads: reserve server-owned fields.
  • PUT preserves every omitted field accidentally: that is partial-update behavior; define it deliberately.
  • PATCH with ambiguous null handling: specify omission/null semantics or use a formal patch format.
  • DELETE returns 204 plus JSON: 204 has no body.
  • Map treated as a database: restart loses data, multiple servers have different maps.
  • Unsynchronized check-then-write: two concurrent requests can both pass a check.
  • Deleting audit records to “close account”: model business closure explicitly.
  • Blindly retrying transfer POST: uncertain outcomes require idempotency or reconciliation.

13. Hands-on lab: beneficiary lifecycle

  1. Add the three records, store, and controller under the root package.
  2. List customer 7's beneficiaries: expect 200 and [].
  3. Create a beneficiary, save its generated ID and Location, then GET it.
  4. Submit the same destination twice: expect 409, no second record.
  5. PUT both writable fields, then try PUT with only name: expect 400.
  6. PATCH the name and confirm destination is unchanged.
  7. Query under customer 8: expect 404 in this fixture.
  8. DELETE, then GET and DELETE again: both should return 404.
  9. Restart the app and explain why records disappear.

Acceptance criteria: all six operations work, IDs are server-generated, parent membership is checked, duplicates use 409, PATCH preserves untouched fields, and 204 has an empty body. Create a request/status/body table before adding new features.

Challenge: support two fictional customers and allow the same destination for different customers while rejecting duplicates within one customer. Move the parent-existence fixture to a small reusable store. Write the exact duplicate predicate and explain why global uniqueness would be the wrong rule here.

14. Knowledge check

1. Does RequestBody validate a positive transfer amount?

No. It binds/deserializes JSON. Semantic constraints require explicit checks or validation annotations and Valid.

2. What belongs in the Location header?

The URI of the newly created resource, so the client can retrieve it.

3. Why must PUT send both writable beneficiary fields?

Our contract defines replacement, not preservation of omitted writable fields.

4. Is this custom PATCH JSON Merge Patch?

No. It is a documented rename operation. Formal patch formats have their own media types and rules.

5. Is one synchronized method a durable transaction?

No. It only coordinates threads using that lock in one process. It does not survive crashes or coordinate multiple instances.

6. Why is changing account balance an unsuitable transfer API?

It bypasses bank-owned rules, corresponding debit/credit, audit, authorization, atomicity, and retry handling.

15. Cheat sheet

POST creates; return 201 + Location + representation. RequestBody reads JSON. PUT replaces writable fields; PATCH applies a defined subset change. DELETE can return 204 with no body. Generate IDs server-side. Treat duplicate/current-state conflicts deliberately. In-memory CRUD is practice infrastructure, not a ledger. Next: extract rules into services and storage behind repositories.
